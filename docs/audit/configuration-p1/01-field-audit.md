# A–B. Auditoría de campos y configuración efectiva

## Cobertura y lectura de la trazabilidad

El descubridor `script/audit/configurationSurfaceP1.mjs` recorre todos los TSX de `client/src`, excluye los primitivos de `components/ui`, tests e iconos, y distingue `wouter.Switch` del control editable. Produce 264 sitios de control y 353 botones/acciones en 42 archivos. Cuenta sitios fuente, no miles de instancias renderizadas; un campo dentro de `map` representa todas las entidades del catálogo. Incluye filtros, autenticación y selección de vista para cerrar la cobertura, marcados INFORMATIVO/fuera de reglas. Los wrappers y sus controles hijos no son capacidades independientes.

Cada entrada de `generated/ui-controls.json` conserva binding, FormField, label localizado, archivo/línea, componente, props, spreads, handler completo, perfil, clasificación, decisión y las 16 dimensiones solicitadas. `generated/ui-traceability.md` es la tabla legible control → clase → evidencia → decisión. `generated/actions.json` cubre guardar, refresh, restore, alta/baja, dependencias inversas, ejecución, locks y navegación: son inventario estático; el script no ejecuta ninguna acción.

Los perfiles contienen la cadena común sin repetirla por entidad. Esta sección resuelve su semántica y sus diferencias de campos. Una clasificación PARCIAL conserva explícitamente el gap de UI, autoridad, provenance o prueba; no equivale a «sin efecto». Los campos adicionales de contratos sin UI se inventarían debajo y en la matriz de capacidades.

## Precedencia real y cortes causales

```text
program_settings + task_templates + zones/spaces + recursos/defaults
  → createPlan: snapshots operativos/plantilla/espacio/recurso/optimizer
  → override diario versionado / override permitido de instancia
  → buildEngineInput (snapshot de plantilla, sin consultar semántica global actual)
  → applyPlanPlannerNextConfiguration (si plans.planner_next_configuration existe)
       taskOperations sobrescribe kind/role/deps/setup/joint/itinerancia/blocksSpace declarados
       reemplaza autoridades Next y neutraliza agrupación legacy
  → applyEffectiveMainFlowPreference (campos efectivos main_* del día)
  → preflightEngineInputForPlannerNext → adaptEngineInputToPlannerNextProblem
  → resolución de scope y contexto protegido → executePlannerNext
  → validatePlan → propuesta/Draft → validación/aceptación Stage → daily_tasks
```

No se interpreta la precedencia conceptual de Fuente 04 como un `merge` universal. `taskOperations` se extiende sobre la tarea ya proyectada y tiene prioridad para sus propiedades; los márgenes y duración no pertenecen a ese objeto tipado actual. `done/in_progress`, locks y Stage aceptado limitan qué puede cambiarse: no son overrides de configuración arbitrarios. Rollback/redo del planning conserva configuración vigente y provenance de los Stages anteriores (`assistedPlanningConfigRevision.ts`, `effectivePlanConfigRevision.ts`).

## Guardar, recargar, cambiar general y restaurar

| Ruta | Guardar/recargar | Cambio global posterior | RESTORE/REFRESH | Riesgo pendiente |
|---|---|---|---|---|
| Horario/comida/transición general | Zod + update + invalidación query; defaults al crear | No debe mutar días existentes | Typed service y baselines; tests locales | Journey browser live no ejecutado; no certificar sólo por GET |

Las pruebas indicadas son evidencia de capas concretas, no una declaración de que todas las filas hayan pasado una prueba UI → DB → run real. Para cada PARCIAL/FALTANTE el backlog fija la prueba que cerraría ese recorrido.
